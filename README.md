# Sentinel frontend

Sentinel's development baseline uses Next.js App Router, React, TypeScript,
Tailwind CSS, and Base UI/shadcn shared primitives. Product pages and branding are
not part of this baseline; the original Next.js starter is preserved at `/ko`.

## Getting started

Use Node.js 24.x and pnpm 10.34.1 (the version in `packageManager`). Install that
pnpm version using your Node toolchain or Corepack if available, then run:

```sh
pnpm install --frozen-lockfile
pnpm dev
```

Open <http://localhost:3000>. `/` returns a temporary 307 redirect to `/ko`,
preserving query parameters. Only Korean is supported; unsupported locales and
unknown pages return 404. Edit `app/[lang]/page.tsx` to work on the starter page.

Installation requires registry access. The pinned `only-allow` preinstall guard
rejects other package managers and may access the registry on first use. Next's
Geist font build also requires Google Fonts access. No backend, secrets, `.env`,
Git remote, or authenticated design session is required for this baseline.

## Quality workflow

```sh
pnpm typecheck       # Generate Next route types, then check TypeScript
pnpm lint            # Type checking and Biome lint
pnpm lint:fix        # Type checking and safe lint fixes
pnpm pret            # Check formatting
pnpm pret:fix        # Apply formatting
pnpm biome           # Type checking, formatting, lint, and import checks
pnpm biome:fix       # Apply safe Biome fixes after type checking
pnpm biome:summary   # Summarize Biome findings
pnpm build           # Production build
pnpm start           # Serve the production build
pnpm dev:secure      # Lint, then develop with experimental local HTTPS
```

Both development commands lint first and enable the Next.js inspector. Route
helper types are generated by `next typegen` before standalone type checking.
The workspace's VS Code settings use the Biome extension; ESLint and Prettier are
disabled locally to avoid competing formatters.

### Local Git gates

Installation runs `pnpm prepare` to activate Husky. Both pre-commit and
pre-merge-commit run `pnpm biome`; failures block the operation without rewriting
or staging files. No remote is needed.

```sh
pnpm prepare
git config --get core.hooksPath # .husky/_
```

Shared hook sources live in `.husky/` and the portable pnpm resolver lives in
`huskyhooks/pnpm.sh`. Generated `.husky/_` files remain ignored. If a GUI Git
client cannot locate Node/pnpm, initialize your existing toolchain in your local
`~/.config/husky/init.sh`; do not put machine-specific paths in shared hooks.

## Shared infrastructure

- **Localization:** `i18n.config.ts` validates the Korean allow-list.
  `utils/localization.ts` loads `localization/ko.json` only on the server. The
  locale layout supplies the complete dictionary to a per-boundary Zustand
  store. `useLocalization()` returns the full state;
  `useLocalization((state) => state.localization.common.ui)` selects a dictionary
  slice. Both expose `lang` and `localization` immediately, without a client
  loading gate. Infrastructure-owned close/loading copy is Korean; the starter
  page is intentionally unchanged.
- **Providers:** the server layout composes next-themes, localization, Query,
  Tooltip, and Sonner. System light/dark mode uses the `sentinel-theme` storage
  key. Generic neutral tokens in `app/globals.css` are library defaults, not an
  approved product design.
- **Primitives:** import directly from `components/ui/<name>`; there is no barrel.
  The baseline includes button, input, label, textarea, checkbox, switch, select,
  dialog, sheet, tooltip, dropdown-menu, separator, skeleton, spinner, badge,
  card, and sonner. `lib/utils.ts` supplies `cn`.
- **Server state:** `providers/query.tsx` creates fresh server QueryClients and
  reuses one browser client. `QueryDefaults` in `constants/query-options.ts` uses
  one-minute freshness and five-minute inactive retention. `QueryPolicy` keeps
  three choices distinct: `defaultRetained`, `freshRetained` (immediately stale,
  retained five minutes, always refetching on mount/focus/reconnect), and
  `noCacheAuthoritative` (the same refetch behavior with no inactive retention).
  Use normal defaults unless the consumer needs a different policy; client
  retention is not server/HTTP caching or an authorization boundary.
- **Ready-to-use libraries:** RHF/Zod/resolvers, date-fns, use-debounce, and Zustand
  are available without empty form, service, or product abstractions.

The baseline was verified with production build/start, locale and asset requests,
passing/failing hooks, both system themes, and a temporary browser fixture for
primitives, native form validation, overlay focus, and query retention. The
fixture was removed; no component gallery, test-runner configuration, hosted CI,
or product-specific assets are included.

## Project-local agent plugins

The complete skill-only plugins from
[SentraLab's plugin registry](https://github.com/KeyWeSmart/sentralab-agent-plugin-registry)
are vendored under `vendor/sentralab-agent-plugin-registry/plugins/`:

- `sentralab-common` 0.1.0: the explicitly invoked Lantern requirements interview.
- `sentralab-web-frontend` 0.1.0: the `sentralab-react-ui-ux` workflow and references.

Source revision: `a3f9e225034827080ff572c3b513b76d9ca28563`.
The plugin files are unchanged copies, not automatically updated dependencies.
To update them, review a newer registry revision, replace both complete plugin
directories, and update this revision after checking discovery.

OMP loads these Agent Plugins 1.0 roots through the relative `extensions` paths
in `.omp/settings.json`. Keep that file and the vendor directories together when
copying this template. Start a new OMP session from the project root; the skills
are available as `/skill:lantern` and `/skill:sentralab-react-ui-ux`. Installing
Lantern does not activate its interview.

Discovery was verified with OMP 18.2.6 without invoking a model. No global plugin
installation, marketplace registration, MCP server, credentials, or frontend
dependency changes are required. The registry is not a marketplace catalog, so
OMP's marketplace install/list commands do not manage these local copies.
Other agent clients need their own supported plugin-loading configuration.

### Vercel performance skill and local precedence

`vercel-react-best-practices` is installed at
`.agents/skills/vercel-react-best-practices/`, with its source and content hash
recorded by the Skills CLI in `skills-lock.json`. The project-local install
command is:

```sh
npx --yes skills add https://github.com/vercel-labs/agent-skills --skill vercel-react-best-practices --agent universal --yes
```

OMP discovers this shared skill location directly; no global installation or
additional agent-directory symlink is needed. Start a new session from the
project root to use `/skill:vercel-react-best-practices`.

The project-owned policy in `.omp/rules/frontend-skill-precedence.md` gives
applicable project requirements and SentraLab's behavior/architecture contracts
precedence over generic Vercel performance examples. It preserves TanStack Query,
fresh-authoritative mutations, stable UI boundaries, and existing theme and
localization ownership.

This is an on-demand frontend rule, not an always-injected global instruction.
OMP lists its task description and file globs for the agent to consult before
relevant work; globs are guidance, not an enforced file-access boundary.
Each project copied from this template can edit or remove this policy without
changing root `AGENTS.md` or either upstream skill. Other clients need an
equivalent project-local rule configuration if they do not read `.omp/rules/`.
